ApexERP – Purchase Order (PO) Integration Gap Report

Scope – Backend (Backend/ERP/Domain/...) and Angular frontend (Frontend/Web/...).
Goal – Verify that the PO flow correctly pulls data from Supplier, Currency, Payment Terms, Lead Time, Price Cards, UOM, and supports Partial Receipt.

1️⃣ Supplier Synchronisation
Item	Implementation found	Gap / Issue	Classification
SupplierId on PO	PurchaseOrder.SupplierId (line 28‑29 of PurchaseOrder.cs)	PO stores only the GUID; no eager fetch of supplier details.	Implemented (store only)
Supplier validation	PurchaseOrderService.CreateOrderAsync validates existence via ISupplierRepository.GetSupplierByIdAsync (lines 119‑126).	Works for existence but does not load supplier‑level defaults (currency, payment terms, lead time, default price card).	Partially implemented

Recommended small backend step

Add a method ISupplierService.GetSupplierDetailsAsync(Guid tenantId, Guid supplierId) that returns the full SupplierDto (already defined).
In PurchaseOrderService.CreateOrderAsync, after confirming the supplier exists, fetch the details and populate PO.Currency, PaymentTermId, LeadTimeDays (new PO fields) with the supplier’s defaults.

6️⃣ Unit‑of‑Measure (UOM)

Recommended small backend step

When a price card supplies a UnitOfMeasureId, assign it to the PO line if the request didn’t specify one.
Introduce a UomConversionService that can convert a quantity from purchase UOM to stock UOM using IUnitOfMeasureRepository.
Apply the conversion in GoodsReceiptNoteService when creating GRN lines (multiply by conversion factor before posting to inventory).
7️⃣ Partial Receipt
Item	Implementation found	Gap / Issue	Classification

Frontend	No Angular component for GRN shown; UI likely posts to a GRN endpoint.	Not verified.	

Recommended small backend step

Add a PurchaseOrderStatus.Fulfilled transition in PurchaseOrderService (or in a domain event) when all Items have ReceivedQuantity >= Quantity.
In GoodsReceiptNoteService, after persisting a GRN, call a method UpdateReceivedQuantitiesAsync that increments ReceivedQuantity on the related PO items.
Add an optional tolerance parameter (maxOverReceiptPercentage) and guard against ReceivedQuantity > Quantity * (1 + tolerance).
Implement a conversion step (see UOM section) before persisting the GRN line inventory.

📋 Recommended Implementation Sequence (backend‑first)
#	Change	Reason / Dependency
1	Add CurrencyId and CurrencyRateAtCreation columns to PurchaseOrder.	Enables snapshot of supplier / company currency.
2	Add PaymentTermId and DueDate columns to PurchaseOrder.	Allows payment‑term linkage and due‑date calculation.
3	Add ExpectedDeliveryDate column to PurchaseOrder.	Uses lead‑time from price card.
4	Extend PurchaseOrderItem with PriceCardId (FK) and PurchaseUomId (if not already).	Stores source of price & UOM.
5	In PurchaseOrderService.CreateOrderAsync – after supplier existence check, fetch supplier details (ISupplierService.GetSupplierDetailsAsync) and populate the new fields (currency, payment term, lead time).	
6	In the same service – when UnitPrice is resolved from a price card, also store the price‑card Id and UOM from the price card (if the request did not specify one).	
7	Implement a UomConversionService (or reuse existing) and adjust GoodsReceiptNoteService.CreateDraftFromPoAsync / CreateManualDraftAsync to convert received quantity from purchase UOM to the product’s stock UOM before posting inventory.	
8	Add tolerance logic to GoodsReceiptNoteService (e.g., 5 % over‑receipt allowed) and throw an error otherwise.	
9	After each GRN creation, call a new method PurchaseOrderService.UpdateReceivedQuantitiesAsync that increments ReceivedQuantity and updates PO status to Fulfilled when all lines are fully received.	
10	Update Angular models (purchase-order.models.ts) to include the new fields (currencyId, paymentTermId, dueDate, expectedDeliveryDate, priceCardId). Adjust the UI/forms to bind them (supplier selection must trigger a call to a new endpoint GET /suppliers/{id}/details that returns the enriched DTO).	
11	Add unit tests for the new service methods (price‑card linking, currency snapshot, due‑date calculation, receipt tolerance).	
12	Run integration tests to verify:
• PO creation with a supplier automatically fills currency, payment term, delivery date.
• Unit price falls back to active price card.
• Partial receipt updates PO line quantities correctly and prevents over‑receipt.
• PO status transitions to Fulfilled after full receipt.	

Note: All migrations should be additive (new columns nullable or defaulted) to avoid breaking existing data. Existing PO records can be back‑filled via a one‑off data‑migration script that copies the supplier’s current defaults where possible.
