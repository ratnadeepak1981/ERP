## 2. Summary of Verified Mismatches & Implementation Corrections

### 2.1 [FINDING-CRIT-01] Missing Filtered Uniqueness on Platform Users and Roles
- **Root Cause:** In EF Core, composite unique indexes `new { x.TenantId, x.Username }`, `new { x.TenantId, x.Email }`, and `new { x.TenantId, x.Name }` had filters generated by EF Core as `[TenantId] IS NOT NULL`. Consequently, when `TenantId IS NULL` (representing global Platform identities), uniqueness was unconstrained in SQL Server, permitting duplicate `admin@platform.local` accounts and duplicate `Platform Admin` roles.
- **EF Core Configuration Corrections:**
  - `Backend/ERP/Security/Infrastructure/Persistence/Configurations/UserConfiguration.cs`:
    - Added filtered unique index for platform usernames: `IX_Users_Username` with filter `[TenantId] IS NULL`.
    - Added filtered unique index for platform emails: `IX_Users_Email` with filter `[TenantId] IS NULL`.
  - `Backend/ERP/Security/Infrastructure/Persistence/Configurations/RoleConfiguration.cs`:
    - Added filtered unique index for platform role names: `IX_Roles_Name` with filter `[TenantId] IS NULL`.
- **Database Migration Generated:**
  - `20261120095707_AddPlatformIdentityUniqueness.cs` (and Designer/ModelSnapshot) in `Security/Migrations/` targeting `SecurityDbContext`.

### 2.2 [FINDING-CRIT-02] Platform Admin & Platform User Seeding Non-Idempotency
- **Root Cause:** `SecurityBootstrapService.EnsurePlatformAdminAsync` and `EnsurePlatformUserAsync` queried users solely by `x.Username == username`. If an account was previously created with email as username (`admin@platform.local`), the lookup failed and attempted to insert duplicate users. Furthermore, `GetSystemRoleAsync` checked `x.IsSystemRole`, missing existing roles if the flag differed.
- **Repository & Service Corrections:**
  - `ISecurityBootstrapRepository.cs` & `SecurityBootstrapRepository.cs`:
    - Updated `GetSystemRoleAsync(string name)` to check `x.TenantId == null && x.Name == name`.
    - Updated `GetPlatformAdminUserAsync()` to check `x.TenantId == null && (x.Username == "admin" || x.Email == "admin@platform.local")`.
    - Added `GetPlatformUserByUsernameOrEmailAsync(string username, string email)`.
  - `SecurityBootstrapService.cs`:
    - Updated `EnsurePlatformUserAsync` to query via `GetPlatformUserByUsernameOrEmailAsync`.
    - Updated `EnsurePlatformAdminAsync` to match both username and canonical email before inserting.

### 2.3 [FINDING-HIGH-01] Customer Portal Canonical Permissions & Role Template
- **Root Cause:** `CustomerRegistrationService.cs` dynamically created `CUSTOMER_COMPANY_ADMIN` with 0 permissions. The central `PermissionCatalogue` had zero customer portal permissions, and `StandardRoleTemplates` did not define `CUSTOMER_COMPANY_ADMIN`.
- **Authorization Corrections:**
  - `Backend/ERP/Security/Boostrap/Permissions/PermissionCatalogue.cs`:
    - Added 6 canonical customer portal permissions:
      - `PORTAL.PROFILE.VIEW` ("View Customer Portal Profile")
      - `PORTAL.QUOTATION.REQUEST` ("Request Quotation via Portal")
      - `PORTAL.QUOTATION.VIEW` ("View Customer Quotations in Portal")
      - `PORTAL.ORDER.VIEW` ("View Customer Sales Orders in Portal")
      - `PORTAL.DELIVERY.VIEW` ("View Customer Deliveries in Portal")
      - `PORTAL.INVOICE.VIEW` ("View Customer Invoices in Portal")
  - `Backend/ERP/Security/Boostrap/Roles/StandardRoleTemplates.cs`:
    - Added `CUSTOMER_COMPANY_ADMIN` to `StandardRoleTemplates.All` with the 6 portal permissions.
    - Updated `StandardRoleTemplates.Build()` so external customer portal roles are strictly segregated from internal employee master data view baselines (`MasterDataViewBaseline`).
  - `Backend/ERP/API/Features/Portal/Services/CustomerRegistrationService.cs`:
    - Updated `customerRole` resolution to locate the standard role template copy and assign all template permissions upon customer company registration.

### 2.4 [FINDING-HIGH-02] Bypassing Normalized Relational Address and Contact Architecture
- **Root Cause:** `TenantMasterDataSetupService` directly inserted flat customer and supplier records into `_db.Customers` and `_db.Suppliers`, bypassing `Addresses`, `CustomerAddresses`, `SupplierAddresses`, `Contacts`, `CustomerContacts`, and `SupplierContacts`.
- **Seeding Service Corrections:**
  - `Backend/ERP/ERP.Application/Features/Setup/TenantMasterDataSetupService.cs`:
    - Added auto-resolution and initialization of default `PRIMARY` AddressType and ContactType.
    - In `SeedSuppliersAsync`: for every supplier with address or contact data, creates normalized `Address` + `SupplierAddress` (with `IsDefault = true`) and `Contact` + `SupplierContact` (with `IsPrimary = true`).
    - In `SeedCustomersAsync`: for every customer with address or contact data, creates normalized `Address` + `CustomerAddress` (with `IsDefault = true`) and `Contact` + `CustomerContact` (with `IsPrimary = true`).
    - Made idempotent: checks existing `SupplierAddresses`, `SupplierContacts`, `CustomerAddresses`, and `CustomerContacts` before adding.

### 2.5 [FINDING-HIGH-03] Customers and Suppliers Missing Default Price Cards
- **Root Cause:** In `TenantMasterDataSetupService.SetupMasterDataAsync`, `SeedPriceCardsAsync` executed *after* `SeedSuppliersAsync` and `SeedCustomersAsync`. Additionally, `Customer.cs` lacked a parameter in `Create()` and a setter method for `DefaultSalesPriceCardId`.
- **Entity & Seeding Corrections:**
  - `Backend/ERP/Domain/Features/MasterData/Customer.cs`:
    - Added optional `Guid? defaultSalesPriceCardId = null` to `Customer.Create(...)`.
    - Added `public void SetDefaultSalesPriceCard(Guid? priceCardId)` method to entity.
  - `Backend/ERP/ERP.Application/Features/Setup/TenantMasterDataSetupService.cs`:
    - Reordered `SetupMasterDataAsync`: `SeedPriceCardsAsync` now runs *before* `SeedSuppliersAsync` and `SeedCustomersAsync`.
    - In `SeedCustomersAsync`: resolves `DefaultSalesPriceCardId` from JSON (if `defaultPriceCard` specified) or falls back to the tenant's first active Sales price card (`SPC-RETAIL-STD`).
    - In `SeedSuppliersAsync`: resolves `DefaultPurchasePriceCardId` from JSON (if `defaultPriceCard` specified) or falls back to the tenant's first active Purchase price card (`PPC-SUP-RET-001`).
    - Re-run safe: updates existing customer/supplier records if their price card foreign keys are currently null.

### 2.6 [FINDING-HIGH-04] Service Products Misclassified as Stock Items with Inventory Tracking
- **Root Cause:** `TenantMasterDataSetupService.cs` lines 405–407 hardcoded `productType: ProductType.StockItem` and `isStockTracked: true`. This violated the domain invariant in `Product.ValidateCapabilitiesAndTracking` when processing `service.json`.
- **Seeding Corrections:**
  - In `TenantMasterDataSetupService.SeedProductsAsync`:
    - Reads `productType` from JSON (`ProductType.Service`, `ProductType.NonStockItem`, `ProductType.StockItem`).
    - If `productType == ProductType.Service`, automatically sets `isStockTracked = false`, `trackingMode = TrackingMode.None`, `reorderLevel = 0`, and `reorderQuantity = 0`.
    - Respects `isStockTracked` from JSON for other product types.

### 2.7 [FINDING-MED-01] Missing Walk-in / Cash Customer Foundation Across All Profiles
- **Root Cause:** All 5 JSON profiles defined only commercial credit customers with `NET30` terms; none defined an immediate cash customer (`CUST-WALKIN`) required for POS, counter sales, and Direct Company Sales.
- **Profile Enhancements:**
  - Added `CUST-WALKIN` ("Walk-in Cash Customer", `IMMEDIATE` payment terms, `00100` Colombo postal code, `IMMEDIATE` credit terms) to:
    - `retail.json`
    - `wholesale.json`
    - `pharmacy.json`
    - `service.json`
    - `manufacturing.json`

### 2.8 [FINDING-MED-04] Hardcoded Workstation Drive Letter in LoadProfileJsonAsync
- **Root Cause:** `TenantMasterDataSetupService.LoadProfileJsonAsync` had hardcoded path `"Z:\\ERP\\Backend\\ERP\\..."`.
- **Seeding Corrections:**
  - Removed hardcoded drive path.
  - Implemented dynamic probing that traverses up to 6 parent directory levels from both `AppContext.BaseDirectory` and `Directory.GetCurrentDirectory()`.
  - Updated the exception message to list all 5 supported profiles: `retail`, `manufacturing`, `wholesale`, `pharmacy`, `service`.

### 2.9 [FINDING-05] Packaging Barcodes Unmapped into Product Identifiers
- **Root Cause:** `packagings[].barcode` was ignored during seeding and never registered in `ProductIdentifiers`.
- **Seeding Corrections:**
  - Updated `SeedProductsAsync` to inspect each packaging's `barcode` property and register an EAN13 barcode in `ProductIdentifiers` if not already present.

## 5. Bootstrap Execution Order & Profile Verification

### 5.1 Initial Bootstrap Execution (Application Startup)

1. **`SubscriptionSeed.Seed(saasContext)`**
   - Populates subscription plans, parameters, and limits in `PlatformDB`.
   - Checks `ExistsByCode` / `ExistsByKey` — 100% idempotent.
2. **`SecurityBootstrapService.EnsurePlatformRbacAsync()`**
   - Seeds `PermissionCatalogue` (all platform and tenant permissions) in `SecurityDB`.
   - Seeds platform roles (`Platform Admin`, `Platform Staff`, `Security Manager`, `Audit`, `Executive`).
   - Seeds `admin@platform.local` account. Checks both username and email to prevent duplicate accounts.
3. **`SecurityBootstrapService.EnsureDomainPermissionsAsync()`**
   - Verifies catalogue permissions; ensures tenant admin role template.
4. **`SecurityBootstrapService.UpgradeExistingTenantsAsync()`**
   - Ensures all standard role templates (now including `CUSTOMER_COMPANY_ADMIN`) are present for every active tenant.

## 7. Outstanding Issues Requiring Business Decisions

The following items are isolated architectural and business policy choices:

1. **Customer Portal Standard Permissions Scope:**  
   Currently, `CUSTOMER_COMPANY_ADMIN` is assigned the 6 self-service portal permissions (`PORTAL.PROFILE.VIEW`, `PORTAL.QUOTATION.REQUEST`, `PORTAL.QUOTATION.VIEW`, `PORTAL.ORDER.VIEW`, `PORTAL.DELIVERY.VIEW`, `PORTAL.INVOICE.VIEW`). Confirm whether customer portal administrators should also be granted permissions to manage other customer contacts within their own company (`PORTAL.CONTACT.MANAGE`).
2. **Automated Master Data Setup in SaaS Tenant Provisioning:**  
   Currently, `TenantProvisioningService` in SaaS provisions PlatformDB and SecurityDB records, leaving DomainDB master data to be initialized through the setup API or onboarding wizard. Confirm whether tenant creation should automatically trigger `TenantMasterDataSetupService` with a default profile (`retail`), or remain an explicit, user-selected onboarding wizard step in the UI.
3. **Obsolete Database Permissions Deprecation Script:**  
   The 18 legacy permissions from early migrations (`USER_CREATE`, `CUSTOMER_VIEW`, etc.) remain in existing development databases. When existing databases are maintained, confirm whether an idempotent cleanup script should set their `IsActive = false` or permanently delete them from `SecurityDB.dbo.Permissions`.
